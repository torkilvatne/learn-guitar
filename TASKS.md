# TASKS — Absolutely Understanding Guitar (support website)

Task breakdown for the whole project. Grouped into epics; each task is a checkbox with a one-line acceptance criterion. See `PROJECT_DESCRIPTION.md` for goals and the "Technical Decisions & Clarifications" section for the locked stack and theory rules.

**Stack:** React + Vite + TypeScript · Tailwind CSS v4 · client-side only · localStorage settings · static build.

**Architecture rule:** all music-theory logic lives in `src/domain/` (pure, no React). Components in `src/components/` are render-only (props in, JSX out). Feature views in `src/features/` compose domain + components. No duplicated theory logic across components.

## Epic 3 — Domain: scale data & engine

- [x] `domain/types.ts`: `Scale = { id, name, altNames?, degrees: number[] }` — a scale is authored as **just its semitones** (0–12, ascending). No generic `category` field — see "Scale metadata model" note below.
- [x] `domain/scales.ts`: all **must-know** scales in `must_know_scales.png` order (Chromatic, Major Diatonic/Ionian, Lydian, Mixolydian, Melodic Minor, Dorian, Phrygian, Natural Minor/Aeolian, Harmonic Minor, Major Pentatonic, Minor Pentatonic, Whole Tone, Diminished, Locrian), each just a `degrees: number[]` literal.
- [x] Add all **exotic** scales from `scales_extended_list.png` (Neapolitan Minor … Harmonic Major), preserving list order.
- [x] Deduplicated: 11 exotic scales turned out to share an identical `degrees` set with another scale already in the list (e.g. Double Harmonic Major = Gypsy = Byzantine). Folded each into the other's `altNames` instead of keeping a separate entry — see "Deduplicated scale names" below. **51 → 40 scales.**
- [x] `domain/scaleEngine.ts`: map a scale's semitones onto the 13-column grid (`GridCell = { semitone, present }`).
- [x] `scaleEngine`: `getNumberLabelForSemitone(semitone)` and `getNoteLabelForSemitone(semitone, rootSemitone)` — both derive their label purely from semitone position via the shared `CHROMATIC_STEPS`/`NOTE_STEPS` reference tables, so **any** accidental degree in **any** scale renders as a dual sharp/flat box (matching `interval_chromatic_scale.png`'s convention), not a single spelling baked in per scale.
- [x] Unit tests: sample scales produce correct grid positions and correct notes for several root notes (A, C, D, F#).
- [x] `domain/quality.ts`: `getScaleQuality(scale)` — derives major/minor/diminished/half-diminished/augmented purely from the raw semitone set (no authored label/step data at all). See "Scale metadata model" below for the one known limitation this simplification accepts.

**Scale metadata model.** There is no generic `category`/`ScaleCategory` field. It previously conflated three unrelated concerns (major-diatonic-mode membership, must-know-vs-exotic provenance, and tonal quality) and was factually wrong for Locrian (excluded from "Major Diatonic Modes"). Replaced with purpose-specific, computed attributes: `getScaleQuality()` (this epic) and `getDiatonicModeInfo()` (Epic 4, below) — both derived from a scale's own semitones, not stored/authored per scale. Must-know-vs-exotic provenance isn't tracked at all since nothing behaves differently for it; list ordering is just the `SCALES` array order.

**Scales are authored as bare semitone arrays, not `{semitone, label}` pairs.** A degree's *display* label (dual sharp/flat for accidentals) is fully derivable from its semitone alone via `CHROMATIC_STEPS`/`NOTE_STEPS`, so authoring it per scale was pure duplication. The one thing raw semitone *can't* recover is which scale-degree-number (2nd, 3rd, 4th...) an accidental note is theoretically functioning as — e.g. semitone 3 could be a `b3` or a `#2`; semitone 6 could be a `#4` or a `b5`. This is a real, provable music-theory ambiguity (Whole Tone's `#5` and Persian's `b6` both sit on semitone 8, needing opposite interpretations, with no way to tell them apart from semitone content alone) — not a coding gap. `getScaleQuality()` handles this correctly for all 7 diatonic modes (the only scales it's actually used for, in Epic 4's roman numerals) using priority rules (perfect 5th always wins; a `b5`/diminished-5th is only trusted when a minor 3rd or natural 4th is also present, so it can't be confused with a `#4` or a competing `#5`) that were verified against every scale in the dataset. The one accepted regression: **Hungarian Major** (`1,#2,3,#4,5,6,b7,8`) is theoretically `major`, but now returns `undefined`, since its `#2` and a hypothetical `b3` sit on the identical semitone and can't be told apart without authored context. This was judged an acceptable trade for eliminating per-degree label authoring across all scales.

**Deduplicated scale names.** Authoring scales as bare semitone arrays surfaced 11 scales whose `degrees` were byte-for-byte identical to another scale already in the list — real, since two culturally/historically distinct scale names can share one interval pattern, but redundant as separate app entries (same grid, same notes, same everything except the label). Folded into the surviving scale's `altNames`: Melodic Minor ← Hawaiian; Harmonic Minor ← Mohammedan (also directly confirmed by `slider.png`, which labels it "HARMONIC MINOR - Aeolian Major 7 - Mohammedan"); Major Pentatonic ← Mongolian, Chinese; Double Harmonic Major ← Gypsy, Byzantine; Hungarian Minor ← Algerian; Kumoi ← Japanese; Major Phrygian ← Jewish, Spanish; Major Locrian ← Arabian. The three must-know-anchored merges (Melodic Minor, Harmonic Minor, Major Pentatonic) had an obvious primary; the other five were all-exotic groups with no must-know anchor, so the surviving name was picked by which is more theory-systematic/commonly used — a judgment call, not a derived fact.

## Epic 4 — Domain: modes

- [x] `domain/modes.ts`: `getDiatonicModeInfo(scale)` identifies whether a scale is one of the 7 major-diatonic modes by checking whether its own consecutive-semitone-step pattern is a rotation of the major scale's `[2,2,1,2,2,2,1]` — not a hardcoded id lookup. Returns the degree (1–7) it starts on, or `undefined`.
- [x] `getRomanNumeral(position, quality)`: whole-numeral case by quality (major → upper, minor → lower), `ø`/`°`/`+` suffix for half-diminished/diminished/augmented — standard theory notation (decided — see PROJECT_DESCRIPTION.md "Roman numeral notation style").
- [x] `getModeProgressionInfo(scale, progression)`: re-roots a diatonic mode's position for `'major'` (Ionian=1) or `'minor'` (Aeolian=1) progression via `((majorScaleDegree - tonicDegree + 7) % 7) + 1`, then derives the numeral from that position + the scale's own `getScaleQuality()`. Major progression cross-checked against the worked G-major example on `resources/SCALES_AND_MODES.pdf` page 18A: `I, ii, iii, IV, V, vi, viiø`.
- [x] `getModesInProgressionOrder(progression)`: the 7 diatonic-mode scales sorted so the progression's tonic is on top.
- [x] Stagger offset for the indented layout, derived (not a separate hardcoded table) as `(naturalSemitone(modeDegree) - naturalSemitone(tonicDegree) + 12) % 12`. `naturalSemitone` is itself derived from `MAJOR_SCALE_STEPS` (its running cumulative sum) rather than a second hardcoded table, so there's exactly one authored fact (`[2,2,1,2,2,2,1]`) driving both mode identification and stagger offsets. Verified against `resources/modes_explained.png`'s visual indentation (each mode's row starts exactly at its root's semitone offset on the shared 2-octave semitone timeline, e.g. Dorian's `1` box lines up under Ionian's `2` box because both sit at semitone 2). Major progression: Ionian 0, Dorian 2, Phrygian 4, Lydian 5, Mixolydian 7, Aeolian 9, Locrian 11. Minor progression (re-rooted at Aeolian): Aeolian 0, Locrian 2, Ionian 3, Dorian 5, Phrygian 7, Lydian 8, Mixolydian 10.
- [x] `domain/search.ts`: `findScalesContainingSemitones` (superset match, for progressively narrowing search-as-you-click) and `findScalesExactlyMatchingSemitones` (exact set equality) — both needs flagged as open in Epic 11 are covered.
- [x] Unit tests for mode rotations, roman numerals per progression, stagger offsets, and search matching (62 tests passing across the domain layer).

**Post-Phase-2 bug fix (user-reported): couldn't reach the last item; the "active" item was consistently off from where it visually centered; clicking a second scale kept the first one marked active.** All three traced to a single root cause: the container div had no `position` set, so `item.offsetTop` (used by `recomputeFocus`/`notifyNearestScale`) was measured relative to the nearest *positioned* ancestor further up the tree — past the header bars — not relative to the container's own content box, while `container.scrollTop`/`clientHeight` (used in the same formulas) *are* always relative to the container itself. The two halves of every distance calculation were silently using different coordinate origins, offset by a constant equal to the header's height. Fixed with one line: `position: relative` on the container, which makes it the `offsetParent` for its children. Diagnosed empirically in a real browser (jsdom can't reproduce this — it has no real layout, so `offsetTop`/`offsetParent` are meaningless there) via temporary instrumentation logging `scrollTop`, `offsetHeight`, `paddingTop`, and each item's `offsetTop` side by side, which showed `item[0].offsetTop` exceeding the container's own `paddingTop` by exactly the header height. Also fixed a related inconsistency in `App.tsx`: `selectedScale` defaulted to `null` (so the header showed nothing on load) while the list itself defaulted to index 0 as visually active — now both default to `SCALES[0]`, consistently. Re-verified all three original symptoms fixed via Playwright against the real dev server (reaching the exact last scroll position, correct active item after a second click, header populated on load).

**Bug fix (user-reported): a visible "twitch" on refresh — the list started at the very top, then jumped to centered "Major Diatonic".** Root cause: `containerHeight` (which the centering `paddingTop`/`paddingBottom` are computed from) starts at `0` and was only measured inside a plain `useEffect`+`ResizeObserver` pair — `useEffect` fires *after* the browser's first paint, so that first paint rendered with `paddingTop: 0` (item 0 flush against the top), and only on the next frame did the real padding apply, visibly shifting everything down. **Bug fix (user-reported): scrolling to a non-Ionian scale then repeatedly refreshing drifted one scale further down the list on every refresh.** This is a browser-side scroll-restoration issue, not a React state bug: Chromium restores a scrollable element's `scrollTop` across a same-page reload using its own heuristics, and — since our snap-alignment bias (`scroll-padding-bottom`, added when fixing the "last scale unselectable" bug two epics ago) was applied via a **JS-computed inline style** — that bias was momentarily absent at the very first paint/parse, when `scroll-snap-type: mandatory` (a *static* class, present immediately) was already active.
